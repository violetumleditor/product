## What it is

Open-source UML editor (Java Swing, originally by Cay S. Horstmann, GPLv2+). Six UML diagram types:
class, sequence, activity, state, object, use case, plus a BPMN one. The same JAR runs:

- as a **desktop app** (default), and
- **in the browser via CheerpJ** (`-cheerpjMode`), driven by `violetproduct-swing/src/main/resources/web/index.html`.

## Build & test

```bash

mvn -B test -pl violet-framework        # one module

java -jar violetproduct-swing/target/violetumleditor-2.3.2-SNAPSHOT.jar   # run (shaded fat JAR)
```

## Architecture essentials

Root package `com.horstmann.violet`.

- **Model** (`product.diagram.abstracts`): `IGraph`/`AbstractGraph`, `INode`/`AbstractNode` (→ `RectangularNode`, `EllipticalNode`), `IEdge`/`AbstractEdge` (→ `SegmentedLineEdge`, `ShapeEdge`). Shared elements (notes, images, points, containers) in `product.diagram.common`. `ContainerNode` (background frame shown as "Grouping area" in the UI, available in all six diagrams; its tool bar prototype draws shapes via `enableToolIcon()`, not an image, since `DarkDiagramGraphics2D` only mirrors colors given to the graphics) is special-cased in `AbstractGraph` (drawn first largest→smallest, found last by `findNode`, never a parent, connected only by a `GenericEdge`); dragging it moves the top-level nodes inside it (`DragSelectedBehavior`). With its tool selected, press + drag on the canvas draws its frame (dedicated `AddContainerByFrameBehavior`, dashed preview; `DragSelectedBehavior` stays idle for this tool); a simple click (`AddNodeBehavior`) or a frame under 10 px creates it at its default size. Either way the tool bar then goes back to the selection tool. With this tool, a press on the selection (incl. anywhere inside a selected container) drags it instead (`BehaviorUtils.isCursorOnSelectedNode`). `FreeTextNode` ("Free text", all six diagrams) is its opposite: no border nor background, drawn upon every element including notes (Z just above them), found first by `findNode`, never a parent, connected only by a `GenericEdge`; its tool bar prototype draws a "T" via `enableToolIcon()`. `ImageNode` ("Image", all six diagrams) is always attached to the graph like notes, so it can overlap other nodes; without image (`image == null`, never persisted) it draws a vector placeholder, both in the tool bar and on the diagram. It keeps its image's ratio, so its size can't follow the grid; its location is put on the grid like the other nodes' (moves by mouse or keyboard), with no centering of its own (a centering on the grid made the opposite corner jump while resizing; user's choice). Its links are kept straight instead by its connection points: `ImageNode.getConnectionPoint` takes `RectangularNode`'s point and moves it along its side onto the grid (absolute position on the graph, half a grid step at most), all in `ImageNode`, no hook in `RectangularNode` (user's choice) (tested by `ImageNodeGridTest`). Dragging a corner resizes it from the opposite corner, which doesn't move at all: `ResizeNodeBehavior` scales the image and its crop insets by one factor (the larger of both axes, so the corner reaches the farthest mouse coordinate) and places the node from the fixed corner; the mouse is taken on the grid, and nothing is computed nor painted until it reaches another grid point (any resizable node); the ratio comes from the image itself, never its scaled, rounded icon, which drifted at each resize (tested by `ImageNodeResizeTest`). Likewise, links sharing a side of a `RectangularNode` are spread along it with their distance to the side's middle rounded to the grid (`getOffsetOnSide`; even spread kept when the side is too short, i.e. two points would meet). `GenericEdge` (all six diagrams, replaces the former `NoteEdge`) is a `SegmentedLineEdge` with every property editable (labels, line style, arrow heads, bent and angle styles); `AbstractGraph.connect` skips `INode.addConnection` for it, so it links any node to any node, itself included, with no rule to learn (user's choice: only an ending node is required); it is the only edge containers and free texts accept. Its defaults (dotted, straight, no arrow) draw like the old note edge, and the diagrams declare it as five prototypes, `GenericEdge.createToolPrototypes()` (Trait, Flèche, Double, Pointillés, Courbé: same class, other properties, so the file format doesn't change; tool tips and short labels in `GenericEdgeStrings*.properties`, the short label `transient`; `getEdgePrototypes(start, end)` offers all five where a generic edge fits; all five are `BentStyle.AUTO` (user's choice: a link from the common tools is automatic, not straight), Courbé also `AngleStyle.ROUNDED2` to show that links can be rounded; only Courbé draws its tool icon going down (transient `bentToolIcon`, `IEdge.getToolIconSlope()`), the others stay horizontal, so straight), and `XMLPersistenceService.resolveTagClass` reads the old `<noteEdge>` elements as generic edges. At the same Z, `AbstractGraph.draw` paints top-level nodes oldest first, so the most recent is on top and found first by `findNode`; children stay before their parent, which paints them again.
- **Plugins**: implement `IDiagramPlugin` (name, category, file extension, graph class) — File > New lists them by notation, then category (`FileMenu.initFileNewMenu`): `getNotation()` defaults to `IDiagramPlugin.UML_NOTATION` ("1.UML", the `file.new_uml_diagram` menu, labelled "UML"); BPMN returns "2.BPMN" and an empty category, so File > New > BPMN > Process diagram (user's choice); order prefixes "n." are stripped + list it in `src/main/resources/META-INF/services/com.horstmann.violet.framework.plugin.IDiagramPlugin`. Shade's `AppendingTransformer` merges those files — keep it, or only one plugin loads. Node/edge prototypes are built in a `static {}` block of each `*Graph` (tooltips freeze to the startup locale). Plugins keep declaring all their prototypes; `GraphToolsBar` splits them in the side bar: an "Outils communs" section at the top, then a section titled with the plugin name (menu prefix `1.` stripped) holding the diagram's own elements then links. The common section holds two 5-column icon grids with short labels, each under a small header (user's choice, mockup "A"): "Éléments" (Select, `NoteNode`, `FreeTextNode`, `ImageNode`, `ContainerNode`; labels from `SideBar*.properties`) then "Liens" (the five generic edges); the diagram's own links are titled "Relations UML" (`graphtools.relations.text`). No paging: the side bar's own scroll pane scrolls, also by dragging its content with the finger or the mouse (`framework.swingextension.DragScrollSupport`, installed in `WorkspacePanel.getScrollableSideBar`: toolkit `AWTEventListener`, past 8 px mostly vertical it scrolls with inertia and disarms the pressed button; mostly horizontal is left to the components, so a node tool can still be dragged onto the diagram). `GraphToolsBarPanel` forwards a button's drags only once `isDragLeftToComponents()` (else an edge tool's first pixel would show its "no drag" warning), and when `isScrollGesture()` becomes true it sends a release (removes the node the press prepared off screen) and selects the former tool again. `ScrollFadeLayerUI` (a `JLayer` around the side bar, viewport in `SIMPLE_SCROLL_MODE` so the fades aren't blitted) fades the top/bottom while tools are hidden there. The diagram section groups its tools by category: the same small header as the common groups (text + line, aligned with them; user's choice: no collapsing, no count), then a 3-column grid of tiles (icon, name wrapped below; `TileGridLayout` skips hidden tiles). A diagram with many kinds of elements declares its categories by overriding `IGraph.getToolCategories()` (record `abstracts.ToolCategory`: name + prototype instances); the prototypes left out, so all those of the six current diagrams, go to the default "Éléments" and "Relations UML" categories. Two parts are pinned out of the scroll pane (`ISideBar.getHeaderAWTComponent()` / `getFooterAWTComponent()`, placed by `WorkspacePanel`): the search field on top (`SideBarSearchField`; while it has a text, `SideBarUI.refreshSearch` shows one section of matching tiles instead of the tool sections, accents and case ignored; it takes the focus only when clicked and gives it up on Escape or a press elsewhere, as typed keys otherwise go to the selected element) and "Style" at the bottom (`SideBarStylePanel`: a `SideBarSection` card like the others, palette icon, open at first, with the palette, the chosen color ringed, and the thickness as a `JSlider` from 1 to 10, not focusable; user's choices: same look as the other sections, thickness by a slider, no reminder of the current style in its header). The style tools show the style of the selection (`ShowSelectionStyleBehavior`, last behavior: no event tells a selection change, so it reads the selection in `onPaint` and calls `IColorChoiceBar.setShownColorChoice` / `IThicknessChoiceBar.setShownThickness`, which display without firing the change listeners, only when the selection or its style changed): the style of the single element, the one shared by several, the default one (`ColorChoice.DEFAULT`, thickness 1) when they differ or nothing is selected; tested by `ShowSelectionStyleBehaviorTest`. The open side bar never gets narrower than it has been (`WorkspacePanel.getSideBarPanel` keeps its widest preferred width): a collapsed section no longer counts in the width, which shrank the sections still open. `SideBar` is `Scrollable` and tracks the viewport width for the same reason: the `JLayer` around it is `Scrollable`, so the viewport doesn't stretch a narrower view by itself. In the rail, a swatch pinned at the bottom (`SideBarStyleButton`, `getCompactFooterAWTComponent()`) opens the same choices in a popup: one shared component, handed back to the panel when the popup closes. In the rail, the five common links take a single such category button, right after the common elements. Below the common tools, the rail always shows one button per diagram category (icon of its tool used last, corner mark) opening a labeled grid beside it, never one icon per diagram tool (user's choice, as on the mockup). Dragging a category button drags the tool it shows onto the diagram, like a tool button: the press is sent only once the gesture is a drag toward the diagram (`DragScrollSupport.isDragLeftToComponents()`), so a click that opens the grid doesn't change the tool. A second click on the swatch or a category button closes its popup: the popup closes on the press before the button gets it, so the button remembers that press (`EventQueue.getCurrentEvent()` in `popupMenuWillBecomeInvisible`) and ignores the click that follows.
- **Workspace** (`workspace`): `Workspace` facade = `EditorPart` (canvas) + `SideBar` + `IGraphFile`. Interactions are `IEditorPartBehavior` classes in `workspace.editorpart.behavior`, wired in `Workspace` / `EditorPartBehaviorManager` (incl. undo/redo handlers and `AutoSaveBehavior`). A node dragged alone can move into another node: `DragSelectedBehavior` asks `IGraph.findNewParentOnDrop(node, mousePoint)` (always a node, never the graph: user's choice; null or the current parent = stays where it is, so a class never leaves its package by drag), outlines that node in dashed violet while dragging (`BehaviorUtils.drawDropTarget`) and moves it there on release (`BehaviorUtils.moveIntoNewParent` → `IGraph.changeParent(node, parent, rank)`, location on graph kept); `UndoRedoOnDragBehavior` (runs after it) records parent and rank (`IGraph.getRank`) at the press and undoes the change in one step (`changeParent` with a null parent puts a formerly top-level node back on the graph). `AbstractGraph.findNewParentOnDrop` is generic: for the nodes a diagram declares (`isMovedByDrop`, false by default), the first node under the point, in `findNode` order, whose `canAddChild` accepts it (not the node nor its descendants, not a container nor a free text). Sequence: activation bars, hence `ActivationBarNode.getImplicitParameter()` walks up the parents instead of caching its lifeline. A bar called by a bar of its own lifeline (self call) stays in its caller when dropped on that lifeline (`SequenceDiagramGraph.findNewParentOnDrop`), and the self call loop is placed from the callee's location on graph, never assuming it is a direct child of its caller (tested by `SelfCallDragTest`). `UserLifelineNode` (sequence, "User lifeline") is a `LifelineNode` whose head is a stick man with the name (not underlined) below it: it only overrides `getTopRectangleHeight/Width` and `drawTop`, so the sequence code must test lifelines with `instanceof LifelineNode` / `LifelineNode.class.isAssignableFrom(...)`, never `getClass().isAssignableFrom(LifelineNode.class)` (exact class only); tested by `UserLifelineNodeTest`. Class: classes and interfaces, into a package (`PackageNode.canAddChild` refuses packages, user's choice; older files with nested packages still load, the reader sets `children` by reflection). Tested by `ActivationBarDropTest`, `PackageDropTest`. A node dragged from the side bar is added to the graph off screen on the press, then moved (`AddNodeBehavior`), and goes into the node it is dropped on at release (a class into a package; undoing the addition removes it from there); when the graph refuses it off screen (an activation bar), it is kept aside (`pendingNodeFromTools`), drawn as a dashed outline at the mouse with the node that will take it, and added on release with `addNodeAtPoint` (undoable) if `canAddNode` accepts the drop point. Once a link is created, `AddEdgeBehavior` goes back to the selection tool (after the current mouse event, via `invokeLater`), so the next drag moves a node; node tools stay selected; with one, a click on a node of the same class selects it (`AddNodeBehavior`) instead of stacking a new one, which matters for notes, free texts and images, always added whatever lies under them. Double tap (or double click) on an empty spot then drag, with the selection tool, moves the view, with inertia (`DragGraphBehavior`; Ctrl + drag still does it with any tool); a plain drag stays the lasso (the user found a long press before the lasso not intuitive). On a touch screen (`LaunchingPreferences.isTouchScreen()`, web page on a tablet or phone; both behaviors read it from the injected `LaunchingPreferences`, `Workspace` unchanged) `SelectByLassoBehavior` does nothing and a plain drag on an empty spot with the selection tool moves the view (user's choice); `AddNodeByTapBehavior` tells a tap from a drag on screen, so a scroll leaves no "+". While held, the cursor is the standard `Cursor.MOVE_CURSOR` (user's choice: a standard cursor, no icon painted on the diagram), set on the editor component itself, as its own cursor hides the scroll pane's. `DragGraphBehavior` comes before `AddNodeByTapBehavior`, which consumes that second press (made on its dashed "+") and hides the "+" instead of offering nodes if the gesture moved; such thresholds are measured on screen (`getLocationOnScreen`), as the editor's coordinates follow the moving view. Escape (`EscapeKeyBehavior`, window key binding, active only while a tool other than Select is chosen) goes back to the selection tool, like a right click. The arrow keys move the selected nodes by one grid step, Shift + arrow by 5 (`MoveSelectedByKeyboardBehavior`, window `KeyEventDispatcher` registered after the typing one, which keeps the keys while typing; same rules as a drag: nodes in a selected grouping area, transition points from `BehaviorUtils.getTransitionPointsToMove` (those of edges between moved nodes + the selected ones, which the lasso selects even on an edge only partly inside, and which also move alone by keyboard; tested by `TransitionPointMoveTest`), never negative; Ctrl + arrow stays select next/previous; text fields, open menus and dialogs keep their arrows); a press until its release is one undoable move (`moveSelectedNodes` / `commitMove`, tested by `MoveSelectedByKeyboardTest`). `EditButtonBehavior` (first behavior of the list) draws a violet pencil button off the top right corner of the single selected node, or beside the middle of the single selected edge, off its line (24 px from the middle segment, along its normal; user's choice: it hid the text typed straight on the edge), on the side opposite to the middle text: the real text's center if any, else the side where `SegmentedLineEdge` would draw it (above a horizontal segment, so the button is below; else right of the segment, up when it goes down to the right, down when it goes up), so it doesn't jump at the first typed character; then still moved off the text (`IEdge.getMiddleLabelBounds()`) if it touches it (state transitions); tested by `EditButtonPlacementTest`, with the selection tool or a node tool (a click with a node tool keeps that tool, and the new node must show it like one dropped from the side bar); a tap on it opens the properties dialog (`EditSelectedBehavior.editSelected()`), as double click is hard on touch screens (same behavior everywhere, no mobile detection). It consumes its gesture's mouse events, and `EditorPartBehaviorManager` stops dispatching an event a behavior consumed. `AddEdgeByDragBehavior` (second behavior) draws a violet link handle just below that pencil, for a node only: drag it onto another node, or tap it then tap the node (Escape or right click cancels). Released (or tapped) on an empty spot, it offers the node kinds linkable to the start node (labeled grid, grouping area left out), creates the chosen one there, then the edge (chosen as below if several fit), node + edge added inside one before/after *edge* event pair so they undo in one step; the new node is selected. `AddNodeByTapBehavior` (third behavior): a tap on an empty spot with the selection tool, while something is selected, only clears the selection (user's choice; the selection is read on the press, before the selection behaviors clear it, so a double click there then only deselects too); while nothing is selected, it leaves a dashed violet "+" there (tested by `AddNodeByTapSelectionTest`) (gone after 5 s untapped — `javax.swing.Timer`, stopped while pressed or while its choice is open — or on any other press, drag, Escape, tool change or selection); a tap on it (so also a double click on the void) shows the node kinds the graph accepts there (`IGraph.canAddNode`, side-effect-free twin of `addNode`, overridden by the sequence/object graphs that refuse activation bars/fields on the graph itself), the chosen one is created there and selected. Same in a node that takes children (`INode.canAddChild`, side-effect-free twin of `addChild`, which calls it: lifeline, activation bar, package, object, field) or a grouping area, the "+" is a plain button, third of the column under the pencil and the link handle (generic, whatever the node's shape: a "+" at the tap point didn't fit an activation bar), shown while that node alone is selected with the selection tool; it offers only its child kinds, created inside it at the first spot from the node's center (a tap in the node leaves no target there: user's choice, the "+" is enough), then moved below each sibling it overlaps (`moveBelowOverlappedSiblings`: a lifeline centers its bars, so a spot found beside a bar put the new one on it; tested by `AddChildByTapOverlapTest`) where `findNode` gives the node itself, not a child. Nothing lies under the finger, so a double click on the node still opens the properties. The link handle's node choice also filters with `canAddNode`. Both place the new node centered on the spot unless its top left corner would fall on another node (`BehaviorUtils.getNewNodeLocation`), and share `ToolChoicePopup` (icon row for edges, labeled 5-column grid for nodes). Offered edges come from `IGraph.getEdgePrototypes(start, end)` (implemented in `AbstractGraph`): only the generic edge if a node is a common element (`AbstractGraph.COMMON_NODE_CLASSES`, also the order of the common tools); else the diagram edges allowed by the diagram's connection rules: each `*DiagramGraph` declares `private static final List<ConnectionRule> CONNECTION_RULES` right after `NODE_PROTOTYPES`/`EDGE_PROTOTYPES` (record `abstracts.ConnectionRule`: start node class, end node class, edge classes; one rule per directed pair, subclasses match; rules follow UML, e.g. a class implements an interface but neither inherits from it nor is composed of it), returned by its `getConnectionRules()` override. The four use case edges share one class (`UseCaseRelationshipEdge`, kept for the file format), so `UseCaseDiagramGraph` keeps them as constants and its rules name edge prototypes instead of classes (second `ConnectionRule` form); the generic edge only if none fits (start node → activity offers the transition alone). `SequenceDiagramGraph` narrows the rules between two activation bars: a return if a `CallEdge` already goes from the end bar to the start bar, else a call (user's choice), so the link is drawn without a choice. Don't dry-run `connect`/`addConnection` instead: they have side effects (a call creates its activation bar, a field reference clears the field value). One kind is added at once, several are shown as a row of tool bar icons (`JPopupMenu` of 44 px buttons) near the release point. The edge is added with the before/after adding events (undoable) and selected; the selected tool doesn't change. Typing a character on a single selected node (selection tool or a node tool, which stays selected once its node is created) replaces its main text, live (`TypeTextOnSelectedNodeBehavior`, a window `KeyEventDispatcher` registered only while the diagram is showing): the property is found by reflection only, no code in the nodes: the first `MultiLineString` field declared (class, then superclasses) that has a getter and a setter (`name`, `text`, `condition` or `signal`; a class's attributes/methods stay in the dialog). Not the bean properties, which the introspector sorts by name (`attributes` before `name`), and the new `MultiLineString` comes from a fresh node of the same class, so it has its defaults (class name LARGE, lifeline/object name underlined). Backspace, Enter (new line, never validates), a click anywhere (also a shortcut or selection change) validates as one undoable property edit, Escape restores the former object, other keys are swallowed (Delete doesn't remove the node). Same on a single selected edge: the typed `String` replaces its `middleLabel` (else `label`, state transitions), found by bean property name; Enter starts a new line there too (user's request: edge texts may hold several lines). Edge labels stay plain `String` fields (file format unchanged) whose lines are separated by `\n`: `SegmentedLineEdge` draws each start/middle/end label as a transient `MultiLineString` (`getLabelText`, small LRU cache keyed by justification + text; `setText` escapes the raw text and turns `\n` into `<br>`; middle centered, an end label aligned on the side of its line), no more `JLabel`, so same font and sizes as the nodes on the desktop and in the browser. A label grows away from its line; on a slanting segment, if its rectangle still reaches the segment (`moveOffSegment`), it moves straight away from the line on its own side until 3 px off. `StateTransitionEdge` draws its label the same way (left aligned; the HTML of an older label, known tags or entities, is still read, anything else shown as typed): no text of a diagram relies on a `JLabel` (user's choice). In the properties dialog, every `StringEditor` property (only edge labels in practice) is a `JTextArea` looking like a text field, growing with its lines and the dialog with it (`CustomPropertyEditor.createMultiLineField`; Enter = new line, Tab = next field; label levelled with the first line). Tested by `EdgeLabelMultiLineTest` (eight directions, real XHTML save and reload). A double click on a text edits it in place (`EditTextInPlaceBehavior`, selection tool, just before `EditSelectedBehavior`, consumes the double click; elsewhere the dialog opens as before; user's choice: a box on the text, edges and nodes). Edge texts first (start/middle/end bounds, `SegmentedLineEdge.getStartLabelBounds` / `getEndLabelBounds`; another edge: its middle `label`): a plain `DiagramTextPane` (`DiagramPlainTextEditorKit`, lines aligned like the label's), writing the String live. Node texts: the graph is drawn again on a 1 px image (no transform), each `MultiLineString` remembering the rectangle it was drawn in (`getDrawnArea`, transient, cleared by `forgetDrawnArea`; the whole compartment, even empty); the smallest area under the mouse among the node's MultiLineString properties wins, edited in the dialog's rich text pane (`MultiLineStringEditor.getTextComponent()`, node's text color), its toolbar floating above the node, unscaled, changing the node's MultiLineString in place (a clone kept for Escape/undo). The box is `ZoomedTextBox`, a transparent child of `EditorPart` (layout `null`): the pane is laid out in graph units and painted through the zoom (mouse events converted), so its text is exactly where the diagram draws it at any zoom (`MultiLineString.getDrawnTextArea()` + `getDrawnTransform()`, rotated for a vertical text like a participant's name; `getLabelBounds`); placed again after each change and on `ZOOM_PROPERTY`. `EditorPart.paintComponent` must work on a copy of its graphics (Swing paints the children with the same one: a zoom left on it painted the box scaled twice, then at its place at each caret blink: user's report) and paint even when valid while it has children, as they are transparent. Enter = new line; Ctrl+Enter, a press on the diagram, a tool change or a permanent focus loss to another component validates as one undoable property edit, only if the user typed; Escape restores; Ctrl+Z/Y act on the box's own `UndoManager` (else the menu would undo the diagram). The texts of an edge belong to it for the mouse (`SegmentedLineEdge.isOnLabel`, part of `contains`; `StateTransitionEdge.contains` likewise; never inside the linked nodes): a click on a text selects the edge, and it is never an empty spot, where the first click of a double click left the "+" of `AddNodeByTapBehavior`, which then caught the second one (the bug of the first version); `AddTransitionPointBehavior` ignores a press on a text. While edited, the text isn't drawn on the diagram, only in the box (user's report: both mixed, as the drawn label moves while it grows): `IEdge.setHiddenText(propertyName)` (transient, `SegmentedLineEdge` / `StateTransitionEdge`), `MultiLineString.setHidden` (transient, size still counts, area still recorded); reset when the box closes. The texts of a `SegmentedLineEdge`, and the label of a `StateTransitionEdge` (its single `labelOffset`), can be dragged (interface `IMovableLabelEdge`; `MoveEdgeLabelBehavior`, selection tool, after `AddTransitionPointBehavior` for its move cursor, before `DragSelectedBehavior`, which doesn't get the drags of a text; user's choices: fixed offset, grid, back home when released near it): the edge saves `startLabelOffset` / `middleLabelOffset` / `endLabelOffset` (`Point2D.Double`, null = automatic place, not written, so older files are unchanged; no editor, so not in the dialog) from the automatic place (`getDefaultLabelBounds`, which follows the edge, so the text follows the nodes); `getLabelBounds(name)` = default + offset, used for drawing, hit test (`findLabel`), bounds, edit button and in-place editing; the top left corner snaps to the grid, under 10 px (screen) from home the offset is cleared; while dragging, a dashed violet line ties the text to `getLabelAnchor` (start, middle of the middle segment, end). One drag = one undoable property edit: `PropertyUtils.setProperty` falls back on the public setter when a BeanInfo lists only the dialog's properties (`GenericEdgeBeanInfo`). Tested by `MoveEdgeLabelTest`. The in-place editing is tested by `EditTextInPlaceTest` (incl. a double click dispatched through `AddNodeByTapBehavior` and `SelectByClickBehavior`). With the selection tool, the element a click would select is highlighted under the mouse (`HighlightHoveredElementBehavior`, added before the selection behaviors: same search as `SelectByClickBehavior`, edge first, else node; translucent violet halo along an edge's shape, rounded violet frame around a node; nothing on a touch screen, on a selected element, while a button is pressed, or once the mouse leaves the diagram). An edge (`ShapeEdge.contains`) is found up to 6 px from its line (was 3), but never inside its start or end node (grouping areas excepted), which keep their clicks (tested by `EdgeHitTest`). Handles (`GrabberUtils`, sizes constant on screen, divided by the zoom): a resize corner is a white square bordered in violet (`drawResizeHandle`), a transition point a round one (`drawTransitionPointHandle`, filled when selected); the one under the mouse (or dragged) is larger, filled violet, in a halo, drawn by `ResizeNodeBehavior` / `CropNodeBehavior` (teal halo) / `SelectByClickBehavior` (transition point of a selected edge, else of the edge under the mouse; `HighlightHoveredElementBehavior` shows the points of a hovered edge). `BehaviorUtils.findResizeDirection` / `findCropDirection` look at the handles of the node selected alone, never the node under the mouse (half of a corner lies outside it, another node may cover it), within 24 px on screen, closest handle first; `SelectByClickBehavior` ignores a press on a handle so the selection survives. `AbstractEdge.findTransitionPoint` (9 graph units, closest point first) is the only transition point hit test (the drag and add behaviors call it); on one, `AddTransitionPointBehavior` shows the move cursor instead of the crosshair. - **BPMN** (`violetplugin-bpmndiagram`, package `product.diagram.bpmn`, menu category "Processus métier"; user's request: intuitive rather than exhaustive, like the usual BPMN modelers). ## Files & persistence (area of recent work)

Package `framework.file`:

- `IFile` (directory + filename), `LocalFile`, `GraphFile`/`IGraphFile` (load, `save(...)`, `saveToNewLocation`, listeners, `isSaveRequired()`), `TempFilenameGenerator` (new diagrams get a temp name and live in the chooser's temp dir until "Save as").
- `file.chooser.IFileChooserService` — abstraction for all file I/O: `chooseAndGetFileReader/Writer` (with optional pre-filled filename), `getFileReader/Writer/Deleter(IFile)`, `getTempDirectory()`. Impl: `JFileChooserService` (desktop) or `CheerpJFileChooserService` (browser).
- `file.persistence`: `IFilePersistenceService` registered as **`XHTMLPersistenceService`** — writes `*.violet.html` (XML embedded in an HTML template `XHTMLFileTemplate.violet.html`), reads it back via the HTML parser and delegates to `XMLPersistenceService`. The page is a self-contained viewer (user's choice among mockups, "mode A"; English texts, no external resource, works from `file://`): full-window diagram on a dotted grid, pan by drag, zoom by wheel/pinch/`+`/`-`, fit by double click/`0`; floating bar = app icon (white flower on a `#6C4EBE` rounded square, both themes, also the favicon), file name + rounded chip of the diagram type (both from the file name, by JavaScript), zoom, theme switch drawn like `MenuBarToolBar.ThemeSwitch`, full screen button (`ToolShapes` corners, hidden where unsupported), black "Get Violet. It's free!" (style of the website's Download button, links to the website), violet "Edit online"; credit at the bottom "This diagram was made with Violet UML Editor <version>" (only the name is a violet link). Template keys: `${version}`, `${image}` (`FileExportService.getImage`), `${imageDark}` (`FileExportService.getDarkImage`, the same rendering through `DarkDiagramGraphics2D`), `${content}` replaced last so a text of the diagram looking like a key stays as typed; the page shows the image of its theme (system's, or the switch's, remembered in `localStorage`). In the browser, the registered service is `new XHTMLPersistenceService(false)` (`UMLEditorApplication`): files saved to the browser storage (save, save as, auto-save) get no images (empty `src`), only Violet reads them back; "Export to > Diagram file", the only download, writes with a `XHTMLPersistenceService(true)` (`CheerpJFileMenuCustomizerCommand.getDownloadPersistenceService`) (user's request). Keep the `<script id="content" type="text/xml"><![CDATA[…]]></script>` block: the reader and "Edit online" depend on it. Tested by `XHTMLFileTemplateTest`. Also `JSONPersistenceService`, `StandardJavaFilePersistenceService`, `Violet016BackportFormatService` (old class-name mapping, plus per-plugin `Violet016FileFilterExtensionPoint`).
- **Backward compatibility of files is a hard requirement** — run the `Legacy*CompatibilityTest`s after any persistence change. Exception: the BPMN diagram, brand new, has no history to keep.
- `AutoSaveBehavior`: always on (despite the `-autoSave` help text); saves after 2 s idle when dirty, and on shutdown; its idle timer restarts on the behavior events and on `IGraphFileListener.onFileModified` (so a behavior that consumes its events, like `MoveSeparatorBehavior`, only needs `graphFile.setSaveRequired()`); on save, syncs opened/recent files in `UserPreferencesService`.
- File menu "Recent files" is rebuilt from preferences by a `MenuListener` each time the File menu opens (a `FocusListener` never fires on a `JMenu`).
- A click on the diagram name in the menu bar renames it (`FileMenu.renameActiveFile`, `GraphFile.rename`, `IFileChooserService.renameFile`). This label exists in all modes: FlatLaf's own title can't be clicked, so it is hidden (`TITLE_BAR_SHOW_TITLE`). On the desktop a diagram with a temporary name goes through "Save as", as it needs a real location. The browser version copies then deletes, the only operations known to work on `/files`. The desktop one uses `File.renameTo`: `Files.move` ignores a change of case on Windows, and writing the new name then deleting the old one would lose the file.
- The active diagram is remembered as soon as it changes or is saved (`MainFrame`), not only at exit: a reloaded web page never goes through `ApplicationStopper`. `DefaultUserPreferencesDao.put` flushes for the same reason, as `java.util.prefs` otherwise writes about every 30 s. At startup, read `getActiveDiagramFile()` before opening the files, since each opened diagram becomes the active one.
- File extensions: `.class.violet.html`, `.seq.violet.html`, `.activity.violet.html`, `.state.violet.html`, `.object.violet.html`, `.ucase.violet.html`, `.bpmn.violet.html`.

## Themes (`framework.theme`)

- Two themes in practice: `FlatLightTheme` and `DarkBlueTheme` (the dark one, FlatDarkLaf + violet accents; the class kept its old name). The older themes stay installed but are only reachable through an old `look_and_feel` preference.
- Choice at startup (`ThemeManager.applyPreferedTheme`): `-theme=` argument, else `look_and_feel` preference, else the system theme (`-systemTheme=` argument, else `SystemThemeDetector`). An empty preference means "follow the system"; the switch at the right of `MenuBarToolBar` writes it (`MainFrame.toggleTheme`), and `-reset` clears it.
- Browser: `index.html` / `test.html` pass `-systemTheme=` from `prefers-color-scheme` and `-theme=` from `localStorage["violet.theme"]`, written by `nativeStoreTheme`. Dialog title bars and frames are DOM elements of CheerpJ (`.cjTitleBar`, `.cjBordered`), colored by the page CSS from `html[data-theme]`: keep them in sync with the themes' menu bar colors.
- Themes switch live, so a component with a custom UI must override `updateUI()` to keep it (see `SideBar`, `GraphToolsBarButton`), or `updateComponentTreeUI` replaces it by the default one. Read theme colors when painting or in `installUI`, not once in a constructor. Theme colors must be constants: never read them from Swing components in `configure()`, it runs under the previous look and feel.
- Diagram files keep their real colors. On screen, `ITheme.getDiagramGraphics` wraps the graphics (`DarkDiagramGraphics2D` mirrors lightness and keeps hue); exports and printing call `graph.draw` directly, so they stay light. Don't take a theme color inside a node's `draw`.
- Menu icons use `shape:<name>` in `MenuFactory*.properties` (`ToolShapes`, drawn by `ShapeIcon` in the menu text color), shared with the tool bar.

## CheerpJ (browser) mode

- Package `violetproduct-swing/.../application/cheerpj/`:
  `CheerpJInterfaceService` (Java `native` methods implemented in JS), `CheerpJFileChooserService`, `CheerpJFileReader`, `CheerpJStorageFileWriter`/`Deleter` (persist in CheerpJ's IndexedDB-backed FS), `CheerpJDownloadFileWriter` (browser download), `CheerpJFileMenuCustomizerCommand` (adjusts File menu in browser mode: Print → PDF tab, Exit hidden, adds "Import from > Local file" (local picker, copied into `/files`) and "Export to > Diagram file" (download); replaces **Open** with a Swing list of the diagrams in `/files` — newest first, trash icon / Delete key per line with confirm, refuses to delete a diagram open in a workspace since auto-save would recreate it).
- JS side: `src/main/resources/web/index.html`. Each native is a function named
  `Java_com_horstmann_violet_application_cheerpj_CheerpJInterfaceService_<method>` and **must also be listed in `cheerpjInit({natives:{...}})`**. Adding a native = Java `native` decl + static wrapper in `CheerpJInterfaceService` + JS function + `natives` entry.
- Launch args used by the page: `-kioskMode -autoSave -cheerpjMode -systemTheme=<light|dark> [-theme=<light|dark>] [-file=/str/<name>]`. Imported files are staged in `/str` (JS-writable, Java-readable); CheerpJ runs Java 17.
- Mobile layout: the page needs its `<meta name="viewport">` (else a 980 px virtual screen) and a `position: fixed` body at `100dvh` (else the address bar area makes the page scroll and hides the menu bar). A maximized frame doesn't follow the display, so once the JavaScript bridge is found, `CheerpJInterfaceService` polls the body size (`nativeGetDisplayWidth/Height`) and resizes every showing undecorated or maximized frame (window resize, screen rotation); nothing to call from the common code.
- Versions: CI publishes the JAR to GitHub Pages both as `violetumleditor-latest.jar` and `violetumleditor-<version>.jar` (older ones kept). `index.html?version=<v>` runs that JAR (`getJarPath`: HEAD check, else latest; `0.0.0` = dev build → latest); the "Open In Online Editor" button of a saved `*.violet.html` passes the `${version}` that wrote it.
- Don't create directories at the VFS mount roots.
- No native `javajpeg` in CheerpJ: `ImageIO` lists JPEG writers/readers but they throw `UnsatisfiedLinkError`, and `new ImageIcon(jpeg)` never returns. So image export is PNG only (all versions, `FileNamingService.getImageExportExtensionFilter`), and on import the page turns the picked image into PNG bytes (`readImageAsPngBytes`) before staging it in `/str`, whatever the file extension.
- CheerpJ gives Java the physical key (`event.code`), not the letter, so shortcuts would depend on the keyboard layout (Ctrl+Z on AZERTY). `useLetterAsKeyCode` in `index.html` / `test.html` rewrites `code` from `event.key` for Ctrl/Cmd + letter.
- Full screen button (right end of `MenuBarToolBar`, `MainFrame.toggleFullScreen`): desktop uses `GraphicsDevice.setFullScreenWindow` (FlatLaf hides its title bar, the menu bar stays); on a scaled Windows screen (125 %), leaving it gives the native window the restored bounds as physical pixels (smaller than Swing believes: menu bar cut off) and drops the maximized state, so `MainFrame.restoreWindowedBounds` sets the saved bounds again (1 px off first, as identical bounds are a no-op) then the saved extended state, in a *later* event (in the same one, maximizing gets physical-pixel bounds, wider than the screen); browser calls `nativeToggleFullScreen` straight from the click (browsers require a user gesture) on the whole page. The state comes from `nativeGetFullScreenState` (-1 unsupported → button hidden, e.g. iPhone), read by the display size follower thread, and the button polls it, since the browser's Escape key also leaves full screen.
- Ctrl+W belongs to the browser (closes the tab) and never reaches the page: in browser mode "Close" has no shortcut (`CheerpJFileMenuCustomizerCommand`; keep shortcuts identical to the desktop rather than adding a web-only one). The page's `beforeunload` handler asks before leaving or reloading **only while a diagram is unsaved** (waiting for its 2 s auto-save): `MainFrame` listens to each `IGraphFile` and calls `CheerpJInterfaceService.setUnsavedChanges` → native `nativeSetUnsavedChanges`. Never ask unconditionally: the user doesn't want the warning once everything is saved.
- Local test without packaging or web server: `mvn compile -Pcheerpj-test` (root dir) writes `violetproduct-swing/target/cheerpj-test/bundle.js` (all classes + jars, base64; generator `violetproduct-swing/src/test/cheerpj/BuildCheerpJTestBundle.java`), then open `web/test.html` via `file://`. `test.html` = copy of `index.html` with a different launch block — keep the JS bridge in sync. See README.

## Conventions & gotchas

- Code style: Allman braces, 4-space indent in most framework code (Eclipse formatter `horstmann.eclipse.code.formatter.xml`); newer CheerpJ classes use K&R — match the file you're editing.
- Resources (`gif/png/properties/xml/html`) sit next to Java sources in `src/main/java` and are packaged from there.
- `MultiLineString` keeps its text as HTML but draws it without any Swing HTML component (helpers in package `abstracts.property.text`, `MultiLineString` itself stays in `abstracts.property`, used everywhere and named in the files): `HtmlTextParser` reads the HTML as lines of `TextRun` (br, p/div, b, i, u, font color/size, span style; the line breaks and indentation of the editor's HTML count as one space, typed spaces are kept), `StyledTextLayout` turns them once into shapes (glyph outlines of the bundled Roboto, `DiagramTextFonts`, `resources/fonts`; system font only for missing characters) and fills them. Nothing may come from the look and feel, the system fonts or the `Graphics2D` (fixed `FontRenderContext`, computed line height = 4/3 of the size), so sizes are the same on the desktop and in the browser: don't go back to a `JLabel`/`BasicHTML` view. The style of the text as a whole (alignment, default size, underline) lives in transient fields but is restored from the HTML, the only thing saved: `XMLPersistenceService` creates a new string and sets its `text` field by reflection, no setter, so `readHtmlStyle()` (called by every getter, setter, `getBounds`, `draw`) takes it from the first block's style (`text-align`/`align`, `font-size`, `text-decoration:underline`; the body's when there is no block) whenever `text` is not the one last synchronized (`textOfStyle`); the setters write it back there (`writeHtmlStyle`). The editor loads `getTextWithoutBlockStyle()`, as its text pane writes back an `align` attribute it has read whatever the alignment buttons do; its underline button turns a whole-text underline into `<u>` tags so that it changes the selection only. The editor's text pane shows the text as the diagram draws it (`DiagramTextEditorKit`: bundled font via a `StyleSheet.getFont` override, body size in `pt` = pixels as Swing's non-W3C units do, paragraph margins 0, every `GlyphView` given a `GlyphPainter` that measures and fills glyph outlines like `StyledTextLayout`, same line height and baseline: Swing's own painter draws hinted glyphs with widths rounded to screen pixels, visibly smaller at 125 %; the editor also drops the `<style>` blocks an older version saved in the texts, which overrode its rules); typed text gets no font size of its own, so it takes the string's default size. `HtmlTextParser` drops the indentation that follows a source line break even after a tag (`<font>\n</font>    </p>`), else it widened the line. A text saved empty tells no style, so it reloads with the plain defaults (a class name typed later in the dialog is then 12, not 16). Tested by `MultiLineStringRenderingTest`, `MultiLineStringEditorTest` and `MultiLineStringStylePersistenceTest` (real save and reload).
- `VersionChecker` still checks for Java "1.6" — obsolete, harmless.
- Commit style: Conventional Commits (`feat:`, `fix:`, `refactor:`, `docs:`).
- Work goes directly on `master` historically; ask before pushing.
